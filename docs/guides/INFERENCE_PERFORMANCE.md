# Скорость ответа, модели и размышление

По умолчанию используется выбранный пользователем сбалансированный профиль.
Настройки читаются при создании агента; после изменения `.env` нужен перезапуск.
Новых зависимостей, загрузки моделей и изменения удалённого хоста нет.

## Последовательность вызовов

Разбор сообщения одновременно возвращает метки ассоциативной памяти. Поиск и запись
памяти внутри диалога и подготовки инициативы больше не обращаются к LLM отдельно.
Если разбор недоступен, используются локальные понятия. Отдельный `/recall` может
дополнить метки через LLM в пределах прежнего дневного бюджета памяти.

В `DIGITAL_CHILD_ANALYSIS_MODE=adaptive` короткие однозначные социальные сообщения
проходят локальный разбор. Цитаты, ирония, вопросы, утверждения и смешанные сообщения
сохраняют смысловой разбор. Значение `always` оставляет его для любых обычных сообщений.
Операторские команды по-прежнему обрабатываются ядром.

Без принудительного исследования и исправления черновика обычно остаются три запроса:
разбор с понятиями, генерация, проверка. Для короткого социального сообщения — два.
Исправление добавляет генерацию исправленного текста и его проверку.

Итог проверяется до callback интерфейса. Явное локальное нарушение сначала отправляется
на исправление, без лишней смысловой проверки уже отклонённого черновика. Исправленный
кандидат проходит обе проверки. Неисправленный ответ заменяется fallback.
При недоступности смысловой проверки остаются локальные эвристики, как и раньше.

## Профили и бюджеты

`DIGITAL_CHILD_LLM_PROFILE`: `fast`, `balanced` или `deep`.

| Задача | Модель по умолчанию | Выходной бюджет |
| --- | --- | --- |
| Короткая социальная реплика / короткий ответ | fast | до 160 токенов |
| Обычный ответ balanced | fast | до 384 |
| Обычный ответ fast | fast | до 256 |
| Сложный или подробный ответ | reasoning, иначе main | общий лимит, обычно 512 |
| Разбор смысла с метками памяти | analysis, иначе fast | 400 |
| Проверка ответа | review, иначе fast | 200 |
| Исправление ответа | fast | до 384 |
| Отдельные метки памяти | memory, иначе fast | 120 |
| Оценка выдержек источников | sources, иначе fast | 600 |
| Самостоятельная реплика | fast | 160 |

Предел `DIGITAL_CHILD_LLM_MAX_TOKENS` сохраняется для ответа и исправления.
Служебные задачи имеют собственные пределы. Windows-шлюз дополнительно ограничивает
каждый запрос своим `WINDOWS_HOST_MAX_OUTPUT_TOKENS`.

Сложность определяется эвристически: большой ввод, блок кода, просьба доказать,
вывести формулу, найти ошибку, сравнить алгоритмы или обдумать глубже.
Deep считает сложными обычные содержательные сообщения; fast отключает автоматическое
переключение на тяжёлую модель. Короткие социальные реплики и отказы не требуют
дополнительного размышления. Подробная длина ответа может увеличить бюджет текста
независимо от профиля. Это выбор ресурсов, а не оценка интеллекта.

Служебный контекст: до 4200 символов для социального общения/инициативы, до 5500 для
обычного ответа, до 7000 для сложного. Общая настройка ограничивает бюджет профиля,
с рабочим минимумом 1600. В текущем вводе сохраняется до 3000 символов, не более
половины бюджета. Символы не эквивалентны токенам. Эти пределы относятся к пользовательскому
пакету контекста; системная конституция и запрос исправления считаются отдельно.

Каждый раздел — свидетельства, память, собеседник, личность, развитие, состояние,
история — получает часть бюджета. Неиспользованный объём перераспределяется.
Решение ядра и текущее сообщение имеют отдельное место; обрезание хвоста больше
не удаляет целые последние разделы при обычных настройках.

## Выбор моделей

Main задаётся прежним `DIGITAL_CHILD_LLM_MODEL`. Fast — через `DIGITAL_CHILD_LLM_FAST_MODEL`,
пустое значение означает main. Дополнительно доступны `ANALYSIS_MODEL`, `REVIEW_MODEL`,
`MEMORY_MODEL`, `SOURCES_MODEL` с префиксом `DIGITAL_CHILD_LLM_`; пустое значение означает fast.
`DIGITAL_CHILD_LLM_REASONING_MODEL` задаётся явно. Без него сложный ответ использует
основную модель без автоматического включения скрытого размышления.

При `/llm` запоминается список доступных моделей. Отсутствующая дополнительная модель
заменяется основной. Если отдельная модель ответа возвращает ошибку до первого фрагмента,
допускается одна попытка fast; частично полученный поток не смешивается с другим ответом.
Пустой SSE не повторяется тем же запросом второй раз.

Текущая Windows-конфигурация ограничивает Ollama одной загруженной моделью. Сохранение
одной модели для большинства ролей избегает дополнительных переключений. Возможность
параллельного выполнения зависит от RAM/VRAM; параллелизм увеличивает расход памяти
контекста. См. [официальный FAQ Ollama](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests).
Клиент не меняет эти настройки автоматически.

## Размышление

`DIGITAL_CHILD_LLM_REASONING_MODE`:

- `auto`: служебные задачи и обычные ответы используют `none`; сложный ответ на явно
  настроенной reasoning-модели использует `DIGITAL_CHILD_LLM_DEEP_REASONING_EFFORT`
  (по умолчанию low) и отдельный `DIGITAL_CHILD_LLM_DEEP_MAX_TOKENS`.
- `off`: везде запрашивается отсутствие размышления.
- `fixed`: ответ использует прежний `DIGITAL_CHILD_LLM_REASONING_EFFORT`; служебные
  задачи и исправления остаются короткими. Если новый режим не задан, старое явно
  выбранное low/medium/high сохраняется через fixed.

Модели с `instruct` в имени получают none. Для несовместимого сервера можно отключить
передачу параметра через `DIGITAL_CHILD_LLM_SEND_REASONING_EFFORT=0`; поведение тогда
определяется сервером. JSON mode отдельно отключается через `DIGITAL_CHILD_LLM_JSON_MODE=0`,
а проверка структуры ответа остаётся.

Ollama поддерживает `reasoning_effort` для моделей с размышлением, но допустимые уровни
зависят от модели. См. [Ollama API](https://docs.ollama.com/api/openai-compatibility#v1chatcompletions)
и [Thinking](https://docs.ollama.com/capabilities/thinking). Параметр не превращает
instruct-модель в reasoning-модель.

Thinking-модели нужен бюджет на размышление и итоговый текст. Перед её включением нужно
согласовать клиентский DEEP_MAX_TOKENS с пределом шлюза: например, явно задать клиенту
1536, шлюзу 2048 и указать уже установленную разрешённую модель. Это пример конфигурации,
а не измеренный оптимум для данного железа. По умолчанию тяжёлая модель не выбирается,
ничего не скачивается. Поля reasoning_content не показываются; распознаваемые начальные
блоки `<think>`/`<analysis>` удаляются перед проверкой и показом ответа.

## Очередь и ошибки

Новые фоновые запросы уступают диалогу в локальном адаптере. Фон не ждёт занятый слот,
диалог ждёт до `DIGITAL_CHILD_LLM_QUEUE_TIMEOUT` (10 секунд). Уже начатый запрос нельзя
мгновенно вытеснить; очередь также зависит от других клиентов хоста. Отменённая
инициатива не запускает дополнительную проверку черновика.

Тайм-аут анализа по умолчанию 10 секунд, источников и инициативы — 30 секунд.
Неудавшаяся оценка источников остаётся незавершённой проверкой и может повториться
по прежней очереди. После сетевой ошибки действует пауза 20 секунд без новых попыток
соединения. Успешная проверка `/llm` снимает паузу; её результат кэшируется на 30 секунд.
Прежний явно установленный тайм-аут основного ответа сохраняется. Тайм-аут чтения
не ограничивает всю длительность потока, если сервер продолжает присылать данные.

## Метрики

`/inference` и `GET /v1/inference` показывают профиль, роли, известные модели,
последние запросы и среднюю длительность по задачам в окне 100 обращений.
Метрики содержат модель, effort, лимит токенов, очередь, длительность, статус,
первый content-фрагмент, finish_reason и usage, если сервер их передаёт.
Промпты, ответы и ключи в них не записываются.

В metadata диалога и HTTP-результате есть `timing_ms` для understanding, memory,
generation, review и delivery. Delivery измеряется до выдачи проверенного текста,
без времени ожидания блокировки агента до начала обработки. Первый content от сервера
не означает, что черновик уже показан человеку. Модель генерации/исправления записывается
в inference; delivered_backend/delivered_model и поля истории учитывают итоговый fallback.
Метрики адаптера хранятся в памяти процесса,
метаданные диалога — в SQLite.

Проверки статические; тесты по прежней договорённости не добавлялись и не запускались.
Настроенный LLM-хост не ответил на чтение списка моделей, поэтому сравнение задержек
на настоящем сервере и совместимость с его установленной версией не измерены.
